What Is TruffleHog?

TruffleHog is an open-source secret scanning tool developed and maintained by Truffle Security. Its primary purpose is to find credentials, API keys, tokens, and other secrets that have been accidentally committed to source code repositories — including secrets buried deep in git history that were "deleted" years ago.

Unlike naive keyword-grep approaches, TruffleHog uses a verified-detection model: each detector actively validates the credential against the target service's API before flagging it. This dramatically reduces false positives and means every result is an actionable finding.

How TruffleHog Works

Scanning Modes

TruffleHog can scan a wide range of sources beyond just git repos:

  • Git — full history traversal across every commit, branch, and tag
  • GitHub / GitLab / Bitbucket — org-wide scanning via API
  • S3 / GCS / Azure Blob — cloud storage bucket scanning
  • Filesystem — local directory scans for CI/CD pipelines or Docker images
  • Syslog / stdin — stream-based scanning for log pipelines

The Detector Framework

The core of TruffleHog's accuracy is its detector system. Each detector is a Go module that implements the Detector interface and handles a specific credential type:

type Detector interface {
    // FromData scans raw bytes for candidate secrets
    FromData(ctx context.Context, verify bool, data []byte) ([]Result, error)
    // Keywords returns fast pre-filter strings to narrow scan scope
    Keywords() []string
}

The scan pipeline works like this:

  1. A source (git, S3, etc.) chunks data into byte slices
  2. The engine runs a keyword pre-filter — only chunks containing a detector's keywords proceed
  3. Matching detectors run regex extraction to pull candidate credential strings
  4. If --only-verified is set, each candidate is sent to the service API to confirm it is a live secret
  5. Verified findings are reported with full context: file path, commit SHA, line number, author, date
# Basic usage — scan a repo's full git history
trufflehog git https://github.com/org/repo --only-verified

# Scan a GitHub org for live secrets across all repos
trufflehog github --org=<org-name> --only-verified --concurrency=4

# Filesystem scan (useful in CI against checked-out code)
trufflehog filesystem /path/to/repo --only-verified

Why It Matters for Blue Teams

Exposed secrets are one of the most common and highest-impact initial access vectors in real breaches. Git repositories are particularly dangerous because git rm does not remove a file from history — a secret committed three years ago is still fully accessible to anyone who clones the repo.

From a blue team perspective, TruffleHog fits into two key use cases:

  • Proactive scanning — integrated into CI/CD as a pre-merge gate so secrets never reach the main branch
  • Incident investigation — retrospective scanning of repos after a suspected leak to determine what was exposed and when

What Makes a Good Detector

Through the contribution process I learned what the TruffleHog maintainers look for in a quality detector:

  • Tight regex — overly broad patterns cause too many false-positive candidates that slow down scanning
  • Minimal keyword set — keywords are substring-matched against every chunk; keep them specific to reduce pre-filter noise
  • Reliable verification endpoint — use a read-only API endpoint that confirms token validity without side effects (no POST/DELETE calls)
  • Graceful error handling — network timeouts and rate limits should not crash the scan; log and continue
  • Test coverage — the project requires unit tests with both valid and invalid credential fixtures

Running TruffleHog in a SOC Context

For ongoing secret hygiene, I run TruffleHog on a schedule against internal repositories and pipe results into our SIEM via structured JSON output:

# Output as JSON for SIEM ingestion
trufflehog git https://github.com/org/repo --only-verified --json \
  | jq -c '.' >> /var/log/trufflehog/findings.json

Alert rules in Splunk watch for new lines in that log source and page on-call if a verified secret is found. From there, the IR playbook kicks in: revoke the credential, audit its usage in cloud provider logs, and determine blast radius before the service owner is notified.

Key Takeaways

  • TruffleHog's verified-only mode means every alert is a real finding — almost zero alert fatigue
  • Git history is permanent; assume anything ever committed is potentially exposed
  • Contributing a detector is a great low-barrier way to contribute to an actively maintained security project
  • Pair TruffleHog with pre-commit hooks (e.g., pre-commit + TruffleHog) to catch secrets before they ever leave the developer's machine
